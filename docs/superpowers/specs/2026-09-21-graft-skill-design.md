# The graft skill: a Claude Code skill that creates or enhances a graftpunk site plugin

Date: 2026-09-21. Status: approved design, validated 2026-09-22, awaiting the implementation plan.

## Summary

graftpunk gains a Claude Code plugin marketplace inside its own repository and one skill in it, `graftpunk:graft`, which walks a developer through the six steps of `docs/PLUGIN_DEVELOPMENT.md` (frame, capture, understand, scaffold, implement, harden) and runs the `gp` commands itself, pausing only where a person has to act: the browser recording and the live login check. The same skill enhances an existing plugin: run inside a plugin project, it records the new flow, proposes commands from the digest, adds the stubs, fixtures, and tests, and runs the project's gate.

Users install it with two commands and see it under `/skills`:

```text
/plugin marketplace add stavxyz/graftpunk
/plugin install graftpunk@graftpunk
```

Invocation: `/graftpunk:graft myshop https://myshop.example/` creates a plugin; `/graftpunk:graft` with no arguments, run inside a plugin project, enhances it. Claude also invokes it on its own when asked to create a graftpunk plugin for a site or to add a command to one.

## Goals and non-goals

Goals: a developer with a site login and no graftpunk knowledge gets a working, tested, publishable plugin package by following the skill, without reading the guide first; the skill copies nothing from the guide and cites only headings that exist, and tests enforce both; everything the skill needs to know or render about a plugin project comes from the package, which is the one tested owner of that format; the skill is versioned and released independently of the graftpunk package.

Non-goals: driving the browser recording from the skill (Claude Code cannot press Ctrl+C in an interactive command); a `gp` pipeline command that bundles digest, scaffold, and fixtures (orchestration stays in the skill, see the rejected approaches; each package change below reports a fact, renders through the existing generator, migrates a project on request, or checks an invariant, and none of those is orchestration); handling secrets in any form.

## Package changes, delivered first

The additions to graftpunk itself, in two pull requests that merge before the skill's (see the ordering at the end of this section), so the skill never carries knowledge the package owns. Each reports a fact, renders through the existing generator, migrates a project on request, or checks an invariant; none orchestrates.

**One owner for "what plugin project is this directory".** A new module, `src/graftpunk/devtools/plugin_project.py`, resolves the working directory to a plugin project (`pyproject.toml`, the `[project.entry-points."graftpunk.plugins"]` table, the module path), classifies it in the directory's own terms (`empty`, `plugin`, or `foreign`, the same names the JSON contract carries, so no layer translates and no non-skill consumer inherits the skill's flow vocabulary), and reads each module with `ast`, never importing it, so a broken plugin still gets an answer. It returns one structural view that every consumer works from, and this list is the view's only definition (the test that pins the view asserts exactly this list): the directory's classification, and for each entry point in the `pyproject.toml` (one for a standalone project, several for a suite) its module path, the plugin class with its source span (there must be exactly one `SitePlugin` subclass per module; the refusal message for anything else is this module's), its `site_name` and `base_url`, each `@command`-decorated method with its span and its decorator keywords (the `endpoint` literal if present), the location of every `GP-FILL` marker in the module, and that plugin's resolved fixtures root (see below); and, for the project as a whole, one boolean per `PROJECT_REQUIREMENTS` entry saying whether its file binds its name (see `gp plugin upgrade`). That is the whole set of facts the info command, the mutator, and the lint need, so none of them parses on its own; the rule is "one read, three consumers", and the view grows here when a consumer needs more, though a need for body-level facts beyond marker locations is the point to reconsider the view rather than extend it. The CLI layer (`src/graftpunk/cli/scaffold_commands.py`, whose docstring says "argument handling only") stays that way: thin entry points calling into `devtools`.

**The digest names the login flow's endpoints, and the skill reads a declared projection of it.** `_login_flow_endpoints`, which the generator computes today in `render.py` to skip the login flow when it renders stubs, moves into the digest model: each `Endpoint` carries a `login_flow` boolean, and the generator reads it instead of recomputing. The skill's proposal table filters on the same field, so the proposal and the scaffold cannot disagree about which endpoints are the login flow. The skill does not read `gp observe digest --json`, which is a reflection over the internal HAR dataclasses and stays what it is, an unversioned diagnostic dump free to change with the analysis code. It reads `gp observe digest --endpoints-json`, a declared projection built by an explicit function in `har/report.py`, not by reflection, carrying only what the proposal step consumes: `schema: 1`, the source (session and run id, or the HAR path), the primary host, and one entry per endpoint with its method, template, `login_flow`, content type, a one-line shape summary (the same string the markdown form prints), query and body parameter names with their observed types, and custom header names; plus a `login` summary listing the observed auth URLs and the form's field selectors, which is what step 3 needs to tell a plain form from a redirect. No cookie names, no token candidates, no example paths, no bodies. Because the projection is an explicit field list, renaming an internal dataclass field touches one function and no contract; the projection's field set is pinned per schema version by a test, fields are added and never renamed or removed within a version, and preflight accepts its number, with the `info` number, through `gp version --json` (see the next paragraph).

**Versioned payloads have one owner.** Three machine surfaces carry a `schema` (the `gp plugin info` payload, the `--endpoints-json` projection, and the fixture sidecar), and the convention is owned once: `src/graftpunk/contracts.py` declares each surface's current schema number and one `refuse_unknown_schema(surface, value)` helper that every package-side reader uses (the sidecar loader today, and whatever reads the other two next), with the add-only rule stated in its docstring. A fourth surface is one new constant. Within the package, `contracts.py` is the only place a schema number is declared (the skill's `SKILL_READS_*` constants are the consumer's expectations, declared in the consumer): the sidecar owner, the `--endpoints-json` projection, and the `gp plugin info` payload builder each read their number from it and never write a literal, and `refuse_unknown_schema` is the only place a number is compared. The numbers are facts about the installed package, not about any directory, so they are reported by the installation's machine surface: `gp version --json` prints them under `contracts` (for example `{"graftpunk": "1.17.0", "contracts": {"info": 1, "endpoints": 1}}`, listing every surface a caller reads through the CLI; each surface's entry lands in the same pull request as the surface, so a release never lists a surface it lacks). Preflight already calls `gp version --json`, so the skill's one version handshake is that one call, before the capture step, against one constant per surface at the top of `preflight.sh`; no reference document carries a schema constant and the model never checks a version mid-flow.

**`gp version --json`, with `--at-least`.** Prints the facts about the installation as data, beside the existing human panel: the installed version and the schema number of each payload a caller reads through the CLI (`contracts`, see the previous paragraph). It is the only machine surface for installation facts, from its first release. It is the bootstrap of every other contract, so it is not itself versioned by a number the caller would need it to read first: its two fields, `graftpunk` and `contracts`, are permanent, fields may be added and never renamed or removed, `contracts.py` states that rule for it beside the rule for the numbered surfaces, and a test pins its field set, and with `--at-least <version>` exits `0` when the installed version is at least that and `1` otherwise. The package has no version ordering today (`_graftpunk_version_floor()` in `scaffold_commands.py` only floors the running version's string to `major.minor.0` for a generated project's dependency line, and nothing compares versions), so `--at-least` introduces the one implementation, ordering with `packaging.version.Version`, and `packaging` becomes a runtime dependency (it is already in every environment that installs graftpunk through pip or uv, as a dependency of their resolvers, and it is the reference implementation of the ordering rule). Preflight never orders versions itself; it compares only schema numbers, as equality. An installed `gp` too old to have the option fails the option parse, which preflight reports as its own exit code (see Preflight).

**A declared endpoint on every generated command.** `@command` gains an optional `endpoint: str | None = None` keyword, stored on `CommandMetadata` and never consulted at runtime or shown in help. The generator writes it on every stub it renders, `@command(help=..., endpoint="GET /api/orders/{order_id}")`, so the endpoint a command implements is a declaration the generator owns, never a deduction from the request call (which the generator renders as an f-string for a parameterised path, so a call-site reader would fail exactly where it matters). A hand-written command may carry the keyword or not. The declaration is a claim with a visible lifetime, not a checked fact: the generator renders `endpoint=` on its own line directly above the request call, with a one-line comment saying to change both together, so a developer editing the stub's request sees it at the moment it can go stale, and the proposal step in enhance mode prints each existing command's declared endpoint beside the rows it excluded, so a stale declaration is visible at the one other moment it matters. This is a deliberate exception to the rule in `devtools/__init__.py` that tooling lives in `devtools` and the top-level API is what a plugin uses: the field is tooling provenance on a runtime object, documented as such in the decorator's docstring, and the alternative (a second, devtools-owned decorator on every generated command) would cost every plugin author more than one ignored keyword does. The exception is recorded here so the rule stays a rule.

**`gp plugin info --json`.** The working directory's plugin project, as one JSON object; every field is a fact about the directory, and facts about the installation (the version and `contracts`) are on `gp version --json` alone. Fields: `schema: 1`; `directory`, the directory's classification in its own terms (`empty`, no `pyproject.toml`; `plugin`, a `pyproject.toml` with the `graftpunk.plugins` entry-point table; `foreign`, a `pyproject.toml` without it), which the skill maps onto its two flows in one line of `SKILL.md` (`empty` is create, `plugin` is enhance) so the contract never carries a consumer's vocabulary; and for `plugin` a `plugins` list, one entry per entry point in the `pyproject.toml` (a standalone project is a one-element list; a suite is longer, and the multiplicity is decided here, before the contract ships, rather than bolted on later), each entry carrying its `module` path, `site_name`, `base_url`, and `commands`, a list of `{name, endpoint}` where `endpoint` is the declared literal or `null` for a command that carries none. Within a schema version fields are added and never renamed or removed, a test pins the field set per schema version so a rename fails the suite, and the payload's `schema` is read from `contracts.py`. The skill accepts the `info` number once, through `contracts` in `gp version --json`; preflight does not compare the payload's own `schema` field a second time. Session facts are not here (the session store is pluggable and may be a remote credentialed backend) and belong to `gp session list`, which the skill calls itself; installation facts are on `gp version --json`. `--json` is the only output form (the command exists for a machine; a human reads `gp plugin new`'s output and the module). Exit 0 for every classification; the classification is data, not an error.

**One encoding for "this endpoint, under this name", with one parser for each half.** Both scaffold commands take `--command "<name>=<METHOD> <template>"`: the name first, then `=`, then the endpoint as the digest prints it. A command name cannot contain `=`, so the split is unambiguous, and the skill, the tests, and the docs carry one shape. The whole value has one parser too, `parse_command_spec` beside `parse_endpoint` in `har/naming.py`, returning the triple (name, method, template) and owning the refusals for an empty name, a missing `=`, or a trailing `=`; both entry points call it, so a malformed value is refused with the same text by both, and neither Typer callback splits anything itself. The `<METHOD> <template>` half already has a private validator in `observe_commands.py` (`_validate_match_patterns`, which exists because a value that splits wrong matches nothing and looks like an empty result rather than a typo); that parser and its refusal move to `src/graftpunk/har/naming.py`, which already owns the method-and-template stem, as `parse_endpoint`, which returns the parsed pair (method, template) rather than only validating, and every consumer takes the halves from it: `gp observe fixtures --match` and its matcher (`_matches_template` in `observe_commands.py` does its own `partition(" ")` today and stops doing so; its fnmatch rule becomes a rule about a parsed template), `gp plugin new --command`, `gp plugin add-command --command`, and the skill's own composition of the string from the digest. The grammar then has one reader as well as one validator. The `--command` wrapper owns only the outer split on the first `=`.

**`gp plugin new <name> --check-name`.** Answers "is this plugin name acceptable, and if not why" without writing anything, by running the same validation `gp plugin new` runs (the name rule `ScaffoldSpec` owns and the reserved-name refusal in `scaffold_commands.py`), so the skill can refuse a name before the capture step while the package stays the one owner of the rule.

**`gp plugin new --command "<name>=<METHOD> <template>"`, repeatable.** With `--from-run`, selects which digest endpoints become stubs and names them, so the names agreed in the proposal step reach the generator instead of being applied to generated code afterwards, and the fixture path rule stays entirely inside the package. Explicit selection is not subject to the twelve-stub cap that applies to the unselected case (`_MAX_SCAFFOLD_ENDPOINTS` in `render.py`). Without `--command` the behaviour is unchanged (every eligible endpoint, generated names, the cap).

**`gp plugin add-command <plugin> --from-run <session> --command "<name>=<METHOD> <template>"`.** Renders one command stub for the named endpoint of the session's newest run (`--run` pins an older one) in exactly the shape `gp plugin new` writes, through a single-command entry point in `render.py` that `gp plugin new` also uses for each of its stubs, and a mutator in `src/graftpunk/devtools/scaffold/insert.py` places it inside the plugin class immediately after the class's last `@command`-decorated method, or, for a class that has no command yet (a hand-written plugin getting its first one), immediately after the class body's last statement, wherever the class sits in the module, using the spans the shared reader returns. The rule is total over any class the reader accepts. The placement policy is therefore code, not a docstring convention, and a module a developer has extended with helpers above or below the class is handled rather than refused; the only structural requirement is the reader's (exactly one `SitePlugin` subclass), and a module that fails it is refused with the reader's reason. Refuses when the command name exists, when the endpoint is not in the digest, and when the digest marks the endpoint `login_flow`. It inserts a stub and does nothing else. Prints the fixture path the command's test will look for (the rule `gp plugin new` prints as its `Next:` line; the generated test module declares the directory as `FIXTURES_DIR` and hands it to `fixture_context`, which builds the `FixtureSession`, and for a suite member that is `tests/fixtures/<plugin>/`, per the fixtures-root rule in `policy.py`).

**`gp plugin upgrade`.** Brings an existing project up to the current generated shape, on purpose and by name. What that shape requires is declared once, `PROJECT_REQUIREMENTS` in `policy.py` beside `PROJECT_GATE`, and the declaration is honest about what the migrator can decide and do: each requirement is a Python file, a module-level name that file must bind, and the canonical statement that binds it (today one entry: `tests/conftest.py` binds `fixtures_are_sanitised`, by the import line the renderer writes). Presence is decided structurally, and the predicate has one owner: the shared reader's view carries, for each requirement in `PROJECT_REQUIREMENTS`, whether the named file binds the name at module level (read with `ast`; a plain import, an aliased import, an assignment, and a wrapped line all bind; a star import and a conditional import do not, and the docstring says so), so a conftest that wires the fixture in any binding spelling reads as satisfied. `upgrade` and `check` both take the answer from the view, so `check` reads the project once and the two consumers cannot disagree about what counts as bound. `upgrade` appends the canonical statement only when the view says the name is unbound, which makes it idempotent under its own definition. A second conftest fixture is one new entry; a `pyproject.toml` key or a gate entry is not this format's business (the first needs a TOML edit through `pyproject_edit.py`, the second is regenerating the README from `PROJECT_GATE`), and the declaration says so rather than promising them. The renderer emits every requirement when it generates a new project (a suite member shares the suite's conftest, which the renderer never rewrites, so for a suite the requirement is decided and applied on the shared file, once), `upgrade` applies the ones a project lacks, and `gp plugin check` reports the ones it lacks; all three read the declaration and none spells a requirement itself, and a test pins the three consumers to it. `upgrade` prints what it changed and changes nothing a project already has; the skill runs it when `check` asks for it.

**One write discipline for every mutator.** `devtools/scaffold/project.py` already refuses before touching anything, undoes partial writes, and restores `pyproject.toml` to its original bytes when an edit fails. That discipline moves into `src/graftpunk/devtools/scaffold/write.py` as the one way `scaffold/` writes: a change is planned against the current bytes, refused with a reason if it conflicts, rendered in full, validated before anything is written by the validator the planned change carries (`ast.parse` for a Python module, `tomllib.loads` for `pyproject.toml`; the writer never switches on file type), written atomically, and restored from the original bytes if any later step of the same operation fails. `write_scaffold`, the stub inserter, and the migrator all go through it, so no path in the package can leave a developer's module half-written or unparseable. The import rule is restated to match what it protects: `policy.py` is imported by readers and writers alike and imports nothing that touches the filesystem; the reader and the lint never import `write.py`; the three writers share it.

**Typed parameters rendered by the generator.** Where a stub parameter has a type in the digest, the generator emits the explicit `PluginParamSpec` entry itself, so the compensation for #208 (introspected options arrive as strings under the future-annotations import) lives in `render.py` and is one edit to remove when #208 lands; the skill says nothing about it.

**A sidecar with one owner, safe to commit by construction.** `gp observe fixtures` writes a `.meta.json` sidecar beside each capture; today it carries `url` (the captured request URL, query string included), `captured_at`, `status`, `content_type`, and `body_params`, as a dict literal inside the CLI command, and `FixtureSession` reads two of those keys by name. The format gets one owner, `src/graftpunk/testing/sidecar.py`, on the pytest-free side of `graftpunk.testing`: it declares the key set of each schema version (version 1: `status`, `content_type`, `body_params`, `capture_sha256`, and `flagged_names`) and the loader, it is the only place a key set is spelled, and it takes the current version number from `contracts.py` rather than declaring one. It sits in the plugin-facing package because `FixtureSession`, which a plugin's tests use, reads sidecars; the writer, which only `gp observe fixtures` runs, lives in `src/graftpunk/devtools/captures.py` and imports the schema from the owner, so the placement rule in `devtools/__init__.py` (plugin-facing API at the top level, tooling in `devtools`) holds on both sides. Every field in it may be committed: `url` and `captured_at` are gone (the HAR and the digest hold them), `capture_sha256` is the hash of the capture body, and `flagged_names` is the cookie and token names the digest recorded for that host. `gp observe fixtures` writes through the owner, `FixtureSession` reads through it, and the sidecar travels with the fixture: the guide's derivation recipe gains one line saying to copy both files into the fixtures root. Nothing reads `url` or `captured_at` from a sidecar today, and `gp observe fixtures` has not shipped in a release, so the change is free.

**Project policy is declarative and lives apart from the writer.** A new module, `src/graftpunk/devtools/scaffold/policy.py`, holds what a generated project must look like and knows nothing about the filesystem: `PROJECT_GATE`, `PROJECT_REQUIREMENTS`, and the fixtures-root rule. `devtools/scaffold/project.py` keeps its job (new-versus-suite, conflicts, writing) and reads the policy like every other consumer, so the read-only consumers (the reader, the lint, the migrator) never import the module that writes to disk.

**The fixtures root has one rule, and the fixtures tree has one root.** `fixtures_root` today takes a `ScaffoldSpec`, which exists only during generation. The per-plugin rule (`tests/fixtures/` for a standalone project, `tests/fixtures/<plugin>/` for a suite member) moves to `policy.py` as a function of two facts, whether the project is a suite and the plugin's module name, and both devtools callers supply them: the generator from its spec, and the reader from the project on disk, whose structural view carries each plugin's resolved root. `add-command` prints it from the view; the generated test module declares its own as `FIXTURES_DIR` and hands it to `fixture_context`, as it does today. The plugin-facing side never resolves a per-plugin root, and the shared `tests/conftest.py` never carries one either, because the generator writes the conftest once, for the first plugin, and never rewrites it when a plugin joins a suite (`add_to_suite` emits four files and no conftest). What the conftest carries is the one fact that is the same in both modes and true forever: the fixtures tree, `tests/fixtures/`, as `FIXTURES_TREE`. Every per-plugin root lies under it, so a check that walks the tree covers every suite member, first or later, without a per-plugin fact ever living in a file that is written once. That keeps the placement rule in `devtools/__init__.py` intact (nothing in devtools is imported by a generated plugin at runtime, and its test suite counts): the import direction is devtools reads policy; `graftpunk.testing` imports neither.

**`fixtures_are_sanitised`, a test the generated suite runs, and the one enforcer of the invariant.** `src/graftpunk/testing/plugin.py`, the pytest side of the existing split, gains a check that the generated `tests/conftest.py` carries (a `PROJECT_REQUIREMENTS` entry) beside `site_env_scrubber`, parameterised by the `FIXTURES_TREE` the conftest declares. It fails if that directory does not exist (the generator creates it with a `.gitkeep`, so a missing tree means the conftest and the project disagree, and that must never pass as "nothing to check"). It walks the whole tree, so a suite member added after the conftest was written is covered like the first. Every fixture anywhere under it must have a sidecar; a fixture without one fails, with a message saying how to produce one (`gp observe fixtures` for a captured file; for a hand-made fixture, a sidecar with `capture_sha256: null` and `flagged_names: []`, which is the author's declaration that the file came off no account, and the check reports on every run how many fixtures it accepted on declaration rather than verified, so the opt-out shows in gate output and in review; the guide states that a declared fixture is trusted, not checked). For every fixture: the sidecar is loaded through the owner, which refuses a missing or unknown `schema` and holds the keys to that version's set (so an old-format or hand-edited sidecar cannot smuggle a URL in, and a later version can add a field without failing sidecars committed under an earlier one); the fixture's hash must differ from `capture_sha256` when one is recorded; and none of `flagged_names` may appear in the fixture body or the sidecar. The check therefore runs in any clone and on the user's CI, with no capture tree present, and `pytest` alone decides the invariant; `gp plugin check` does not restate it. Its limits are stated in the guide and in the check's docstring: it catches a missing sidecar, an unchanged copy, a leaked flagged name, and a sidecar outside its declared format; it does not judge whether invented content is invented well.

**`gp plugin check`, a lint in `src/graftpunk/devtools/plugin_check.py`.** Works from the shared reader's view and reports, listing each finding: a remaining `GP-FILL` marker; a module without exactly one `SitePlugin` subclass; and a `PROJECT_REQUIREMENTS` entry the project lacks, which `gp plugin upgrade` fixes. It does not compare a declared endpoint against the request call: the declaration is authoritative by design, the call site is unreadable exactly where it matters, and a check that could only ever be weak would give an author a reason to drop the keyword that enhance mode depends on. It is a lint, not a test, so a freshly scaffolded project's test suite still means what test suites mean, and it never edits.

**The project gate and the project's requirements have one owner each.** The list of commands a generated project's gate runs is one constant, `PROJECT_GATE` (`pytest`, `ruff check .`, `ruff format --check .`, `gp plugin check`), in `policy.py` beside `PROJECT_REQUIREMENTS`, and it is reproduced in exactly one rendered form, the fenced checks block the renderer writes into the generated README. The guide's "The gate" section quotes that same block verbatim, and the guide's CI workflow example runs it as one `run:` step whose lines are that block, so one extractor (a fenced block's lines) pins both guide copies to the constant, the way `tests/unit/test_project_description.py` pins the README's CLI block to `gp --help`. The guide's "Before you publish" checklist refers to the gate by name ("the gate is green") and keeps only the items the gate cannot check (nothing about markers or individual commands); it reproduces no command and is not a pin. A second test pins the constant's `gp` entries to the live CLI through the walker `tests/unit/test_plugin_development_guide.py` already has, so a renamed command fails the suite instead of shipping a stale gate. The skill's `harden.md` points at the guide's section and runs whatever it lists; the skill never enumerates the gate.

The plan orders the work as three pull requests, so review, revert, and bisect are not all-or-nothing: first the pieces that stand on their own (`contracts.py`, the sidecar owner and the committable format, `login_flow` and the versioned `--endpoints-json` projection, `gp version --json --at-least` with the `packaging` dependency, `gp plugin new --check-name`, `policy.py`, `parse_endpoint`, `write.py`, and the `render.py` split), each with its tests; then the pieces that need the reader (`plugin_project.py`, `gp plugin info` with its `contracts.py` constant and its `contracts` entry, `--command`, `add-command`, `upgrade`, `check`, the sanitisation check and its conftest wiring), with the guide's "The gate" section, recipe line, and checklist; then the marketplace and the skill. The first two ship in one minor release of graftpunk, which the skill's `SKILL_REQUIRES_GRAFTPUNK` floor names. `plugin_app`'s help string becomes "Scaffold, extend, inspect, and check a graftpunk plugin project". The four new entry points join `new` in `src/graftpunk/cli/scaffold_commands.py`, which keeps owning `plugin_app`, its `register()` on the root app, and the reserved-name snapshot, and stays "argument handling only" (each entry point is a few lines calling into `devtools`). The split of that module into generation and inspection halves is deferred with a stated trigger: the next command added to `plugin_app` after these, or the module passing 400 lines, whichever comes first; at that point `plugin_app` and the snapshot move to a small module both halves import, and `main.py` imports both halves so registration by import side effect cannot silently drop a command. `render.py`, the module that actually grows (1190 lines today, and four of the features above route through it), is split in the first pull request along the seam already visible in it: the Python-source formatting helpers (identifier and literal rendering, wrapping, escaping) move to `src/graftpunk/devtools/scaffold/pysrc.py`, and `render.py` keeps the per-artifact renderers; that is item 2 of issue #201, closed by the same change.

## The skill

### Frontmatter

```yaml
---
name: graft
description: Create a graftpunk site plugin from a browser recording, or add commands to an existing one. Use when asked to build, scaffold, or extend a graftpunk plugin for a site, or to add a command to a plugin.
argument-hint: "[plugin-name] [site-url]"
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/preflight.sh *) Bash(gp plugin info *) Bash(gp session list) Bash(gp observe list) Bash(gp observe digest *) Bash(gp observe fixtures *) Bash(gp plugin new *) Bash(gp plugin add-command *) Bash(gp plugin upgrade *) Bash(gp plugin check *)
---
```

`disable-model-invocation` stays at its default (false), so Claude can invoke the skill from a plain request. The pre-approved list is declared, not derived: it is the boundary, and the rule for what belongs on it is stated in `SKILL.md` above the list (the commands the eight steps run unattended that touch neither the live site nor a credential). The commands the steps run are themselves declared, not narrated: `skills/graft/references/commands.md` lists them step by step in fenced `bash` blocks, `SKILL.md` and the other references describe them in prose however reads best, and that one file is the referent the skill's test (see Testing) binds the list to, in the direction that cannot widen consent on its own: every `allowed-tools` entry must match a command in `commands.md` (a stale entry fails), and the two exclusions must stay absent; a newly declared command is not pulled onto the list by the test, it needs a deliberate edit to the frontmatter, and a reworded sentence can never look like a consent change. The deny side (`gp <plugin> login` and the live-site commands) is a hand-maintained pair the test asserts absent, not a derived set, and `SKILL.md` says so beside the list. Writing inside the project tree is not an exclusion axis: producing the project is the skill's job, and every write these commands make is to files the user asked the skill to produce (`gp observe fixtures` writes under `tests/captures/`, `gp plugin new`, `add-command`, and `upgrade` write the project). `gp <plugin> login` and any command against the live site are therefore absent and go through the normal permission prompt, which is the user's go-ahead for the live check; `gp observe show` is absent because no step runs it. A later "add `gp x` to avoid a prompt" edit is a two-file change that shows in the diff as a test change.

### Modes

The mode comes from the working directory: preflight runs `gp plugin info --json` (see Package changes, delivered first) and relays its answer, whose `directory` field classifies the directory in its own terms, and `SKILL.md` maps that onto the skill's two flows in one line.

- `directory: empty` (no `pyproject.toml`): create mode, scaffold into the working directory.
- `directory: plugin` (a `pyproject.toml` with a `[project.entry-points."graftpunk.plugins"]` table): enhance mode; the answer carries a `plugins` list with, per entry point, the module path, `site_name`, `base_url`, and every existing command with its declared endpoint, or `endpoint: null` for a command that has none. With one entry the skill takes it; with several (a suite) it takes the plugin named by `$0` when one was given and matches an entry, and asks which one otherwise.
- `directory: foreign` (a `pyproject.toml` without that table): stop with "this directory holds a project that is not a graftpunk plugin; run the skill in an empty directory or in the plugin's project".

Arguments: `$0` is the plugin name and `$1` the site URL in create mode; both are ignored with a note in enhance mode, where the plugin name comes from the package's answer. A create-mode invocation with no arguments asks for the name and the URL, one question each.

### The flow

Each step names the guide heading it follows. The skill reads a reference file only at the step that needs it, and reads the guide section itself only when the reference says to.

1. **Frame** (guide: Frame). Create mode collects the plugin name (validated against the name rule the guide states; the name is checked by the package before the capture step with `gp plugin new <name> --check-name`, which writes nothing, exits `0` when the name is acceptable, and otherwise exits `1` printing the same refusal `gp plugin new` would give; the skill carries no copy of the name rule and no list of reserved names), the site URL, and what the user wants to do on the site, in plain words: "see my orders and download invoices" is enough. It does not ask for command names or endpoints; those come from the digest. Enhance mode collects only the new thing the user wants to do. The login shape and the backend are decided by the skill from the digest later, and confirmed with the user only when the digest is ambiguous (an identity-provider redirect, or no login at all).
2. **Capture** (guide: Capture). The skill prints the exact command for the user to run in the session with the `!` prefix, `! gp observe --no-session interactive <url>`, tells the user to log in, exercise every flow they named, and stop with Ctrl+C, and then waits. UNVERIFIED: that a Ctrl+C typed during shell mode (https://code.claude.com/docs/en/interactive-mode) reaches `gp` as SIGINT so the HAR is saved; the interactive-mode documentation describes Ctrl+C only as interrupting the running operation. The plan's first task probes this on the workstation; if it does not hold, the hand-off tells the user to run the recorder in a separate terminal instead. When the user says the recording is done, the skill runs `gp observe list`, takes the newest run for the inferred session name, and repeats the name back. It never runs the interactive command itself.
3. **Understand** (guide: Understand). The skill runs `gp observe digest <session name> --endpoints-json` (whose schema preflight already accepted), reads the projection, and proposes the commands: a table with one row per candidate (name, what it returns, the endpoint behind it, the parameters seen), mapped to the wants the user stated, with any want that has no endpoint named as needing another recording. The rules that build the table live in `digest.md` and are stated once, in "The command proposal, in detail" below. The user keeps, renames, or drops rows in one answer.
4. **Scaffold** (guide: Scaffold). `gp plugin new <name> --from-run <session name> --command "<agreed name>=<METHOD> <template>"` once per row the user kept (the newest run for that session; `--run <run id>` pins an older one). The generator writes only those stubs, under those names, with the request call it decides for each endpoint and the endpoint declared on each. The skill edits nothing the generator wrote in this step.
5. **Implement** (guide: Implement). For each stub: fill the request, name the parameters, decide the return shape, and replace every `GP-FILL` marker. Errors raise `CommandError` or `PluginError`.
6. **Harden** (guide: Harden). `gp observe fixtures <session name> --match "<METHOD> <template>"` for each command; each captured file and its sidecar are copied into the project's fixtures root (the guide's recipe, extended to name the sidecar) and the fixture's content is invented with its structure kept. The generated project's own suite proves the copy was changed and leaks no flagged name (`fixtures_are_sanitised`, under Package changes), one test per command with `fixture_context`, then the project's gate as the guide's "The gate" section lists it (the package owns the list; it includes `gp plugin check`, which reports a remaining `GP-FILL` marker, so step 5 cannot be skipped). When `gp plugin check` reports missing project wiring, the skill runs `gp plugin upgrade` and reruns the gate. The gate has to pass before the next step.
7. **Kick the tires** (guide: Check the CLI surface you shipped, and Login). With the user's go-ahead, the skill runs `gp <name> --help` and checks every agreed command name is there, then `gp <name> login` and one read-only command against the live site while the user watches. Credentials come from the environment or the workstation env file, which the user sets up (the skill prints the `gp config set` lines with placeholders and never the values). A login failure is diagnosed against the guide's Login section (the failure text, the success signals, the timeout) and the plugin's `LoginConfig` adjusted; the check reruns once.
8. **Publish checklist** (guide: Before you publish). The skill reads the guide's checklist section, whose first item is "the gate is green" (already true after step 6) and whose remaining items are the ones no check can decide, as the guide lists them (the skill does not carry its own copy of that list), walks those, fixes what it can, and stops with the remaining items listed for the user.

The skill restates the step it is on at the start of every turn by name (one line: "Step: scaffold. Done: ...; next: ..."), never by count, so adding or removing a step touches one place, and asks one question at a time.

### Where enhance mode differs

The eight steps above are written for create mode. Enhance mode runs the same steps with exactly these differences, and this list is the only place they are stated, so a change to enhance mode is one edit here:

- Step 1 collects only the new thing the user wants to do; the plugin name, `site_name`, and `base_url` come from `gp plugin info`.
- Step 2 runs `gp session list` and records with `-s <session name>` when it lists a session for the plugin, and with `--no-session` otherwise.
- Step 3 excludes the endpoints existing commands declare (`gp plugin info` reports each command's `endpoint`) and prints each excluded row with the existing command's name and declared endpoint beside it, so a declaration that went stale after a hand edit is visible where it matters; marks every remaining row as new; and, for each existing command reported with `endpoint: null`, adds a row of its own that says "existing command, endpoint not declared" so the user can say whether a proposed row duplicates it. The skill never silently drops or silently proposes over an undeclared command.
- Step 4 does not run `gp plugin new`. For each agreed command it runs `gp plugin add-command <name> --from-run <session name> --command "<agreed name>=<METHOD> <template>"`, which renders one stub in the generated shape into the plugin class and prints the fixture path its test will look for.
- Step 8 is limited to the checklist items the new commands touch.

### The command proposal, in detail

The user should never need to know the commands in advance. The digest is the source: every first-party, non-static endpoint the recording saw, with its method, templated path, query and body parameters and their observed types, shape summary, custom header names, and `login_flow` flag. The markdown form prints the first `--limit` endpoints (default 60) and says how many it held back, so the skill reads the `--endpoints-json` projection, which is uncapped and carries exactly those fields and nothing else. The shape of the request call a command makes (`request_json` or `request_text`, and its role) is the generator's decision, made when it renders the stub; the proposal table reports what the digest says about an endpoint (its content type and shape) and never restates that rule. The skill turns the model into a proposal by these rules, in order:

- Drop every endpoint the digest marks `login_flow` (the same flag the generator skips when it renders stubs, so the table and the scaffold agree), and trust the digest for the rest: static assets, analytics and tracking hosts, and anything on a host other than the primary one never reach the endpoint list at all.
- Keep JSON endpoints and HTML documents that carry the user's own data (a dashboard, an order list, a statement page); drop navigation chrome.
- Name each kept endpoint as a verb phrase a person would type: `orders` for `GET /api/orders`, `order` for `GET /api/orders/{order_id}` (the path parameter becomes the command's argument), `invoice-pdf` for a document download. Collapse a list-and-detail pair into two commands, never one.
- Present the proposal as a table with one row per command: name, what it returns (from the shape), endpoint, parameters. Say which of the user's stated wants each row serves, and name any want with no endpoint behind it.
- Ask one question: "keep, rename, or drop any of these?" and apply the answer. A want with no endpoint gets the capture step again for that flow, appended to the same run name.

In enhance mode the same rules apply to the new recording, minus the endpoints the existing commands already use.

### The references

Each reference is short (under 120 lines) and holds only what the skill needs at the step that reads it; anything the guide already says is cited by heading and read from the guide at that point, never copied. `rules.md` is an inventory: one line per house rule, each naming the guide heading that states it (entry point registration, never commit a capture, fixtures invent content, parsers never return a confident empty list, exact failure text, secrets from the environment only, resolve a secret by what it is), and the skill reads the cited section when a rule applies. `capture.md` holds the hand-off text and the "what to exercise" prompts, which exist nowhere else. `digest.md` holds the command proposal rules (their single home; the section below is the design that produced them) and a worked example on the guide's synthetic digest; its login-flow rule is "drop what the digest marks `login_flow`", the same flag the generator reads, so the reference restates no package logic. `harden.md` holds the fixture derivation recipe and the test shape, and for the gate and the publish checklist points at the guide's "The gate" and "Before you publish" and tells the skill to read them.

### Preflight

`skills/graft/scripts/preflight.sh`, bash, needing only `gp` on the path. It owns exactly what must be decided before anything else runs and nothing it would have to interpret: it checks that `gp` is present and new enough, makes the one version handshake against `gp version --json`, runs `gp plugin info --json`, prints both answers unchanged as one JSON object (`{"installation": <gp version --json>, "project": <gp plugin info --json>}`), and exits:

- `0` with that JSON on stdout (the `directory` classification and the project facts are the package's answers; preflight adds nothing and interprets nothing beyond the handshake, so mode policy has one owner, the skill).
- `2` when `gp` is missing, with the install line (`uv tool install graftpunk` or `pip install graftpunk`).
- `3` when `gp version --json --at-least "$SKILL_REQUIRES_GRAFTPUNK"` exits `1`, with the upgrade line. `SKILL_REQUIRES_GRAFTPUNK` is a constant at the top of the script, set to the release that ships the package changes (the name is distinct from `scaffold_commands.py`'s `_graftpunk_version_floor()`, which is the version a scaffolded project depends on). `gp` has no `--version` option and `gp version` prints a Rich panel for people; the package answers the ordering question, and preflight never reads rendered text and never compares version numbers.
- `3` as well when a number under `contracts` in `gp version --json` is not the one the skill was written for (`SKILL_READS_INFO_SCHEMA` and `SKILL_READS_ENDPOINTS_SCHEMA`, the only version constants the skill carries, one per payload the skill parses), so a package that moved a contract the skill reads cannot be misread. The message names the direction: a package number above the skill's constant means the skill is older, and the fix is `/plugin marketplace update graftpunk` then `/plugin update graftpunk@graftpunk`; a package number below it means graftpunk is older, and the fix is the upgrade line. The sidecar has no skill-side constant: the skill copies sidecars that `gp observe fixtures` wrote and never parses or writes one, and the generated suite's loader enforces the sidecar's version, so a sidecar version bump never blocks an older skill.
- `5` when `gp` rejects an option preflight passed (`--json` or `--at-least`), which is either an installed `gp` older than the floor or a skill bug passing a misspelled flag; the message names both readings and the upgrade line, so a skill bug never masquerades as "upgrade graftpunk" alone.

The skill runs preflight first on every invocation and stops on any non-zero exit, printing the script's message verbatim; on `0` it reads `directory` and applies the Modes section, including the stop message for `foreign`.

## Errors and secrets

Every `gp` command's failure is shown to the user verbatim, the cause diagnosed against the guide, and the step retried once after the fix. No step is skipped, and no failure is summarised away. The skill never asks for a password, never writes a credential anywhere, never prints a `gp config get --resolve` result, and never reads a value that came off the account: not a cookie or token value, not a HAR body, not a capture. What it reads from a recording is the `--endpoints-json` projection alone, which by construction carries endpoint names, parameter names and types, and the login form's selectors, and no cookie names, token candidates, example paths, or bodies. It passes run names and match templates to `gp` and reads only that projection, the fixtures directory, and the generated project. When the user pastes a secret into the conversation, the skill says where it belongs (`gp config set NAME '$(your-secret-tool read ...)'`) and does not use it.

## Versioning and release

The skill's version is independent of the graftpunk package version. Any change under `skills/` requires a patch bump of both `version` fields (`.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`), because Claude Code caches an installed plugin under a version-stamped path, `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, and a new version string means a new cache directory (https://code.claude.com/docs/en/plugins-reference). UNVERIFIED: that an unchanged version string leaves stale content in place. The documentation does not state it; `stavxyz/skills` RELEASING.md reports the cache "isn't reliably invalidated when the version is unchanged" and cites claude-code issues #46081, #14061, and #17361. Minor bumps are for a new skill or a changed invocation contract.

One guard, in CI. `.github/workflows/skill-version.yml` runs on pull requests: when the diff against the base commit touches `skills/` or `.claude-plugin/`, the two version fields must be equal to each other and different from the base's; otherwise the job fails and names the next patch. The check is `scripts/check-skill-version.sh <base sha>`, also runnable by hand and as `just skill-version` before pushing. No git hook: `core.hooksPath` is repository-wide and exclusive, and a local backstop for a check that already blocks the merge is not worth that commitment.

After a merge, users update with `/plugin marketplace update graftpunk` and `/plugin update graftpunk@graftpunk`.

- The `--endpoints-json` projection carrying `schema: 1` with its field set pinned, carrying no cookie names, token candidates, example paths, or bodies (asserted on the sample HAR's digest, which has all four), and surviving a rename of an internal `Endpoint` field without a change to its output (asserted by building the projection from a digest whose dataclass was patched), while `--json` stays unpinned.
- `PROJECT_GATE` matching the generated README's checks block, the guide's "The gate" block, the guide's CI example, and the guide's publish checklist's first item, and each of its `gp` entries resolving through the CLI walker.
- `PROJECT_REQUIREMENTS` pinned to what the renderer emits, what `upgrade` applies, and what `check` reports (one entry added in the test makes all three follow).
- The fixtures-root rule in `policy.py` giving the same answer from a spec and from the project it generated, for a standalone project and a suite member, and the generated test module's `FIXTURES_DIR` equalling that answer while the conftest's `FIXTURES_TREE` contains it.

A full dry run of the skill (create mode against a recording of a real site, or `gp observe digest --har tests/fixtures/sample.har` where a live capture is not available, then enhance mode adding one command) is a manual test-plan item on the pull request, recorded with the commands run and their output.

## Rejected approaches

A thin skill that only tells the model to read the guide: no duplication, but every run reloads 1,100 lines, the per-step checklists that make a run reliable are missing, and nothing pins the skill to the guide's headings. A `gp plugin dev` pipeline command that runs digest, scaffold, and fixtures in one go: fewer model steps, but it moves orchestration into the CLI as a new product surface with a release dependency, and enhance mode needs judgment a pipeline cannot supply. Two skills (`new-plugin` and `enhance-plugin`): the flows share six of eight steps, so they would drift.

## Out of scope

The introspector's handling of string and optional annotations (#208; the skill works around it with explicit `PluginParamSpec` entries). Naming a first capture and `gp plugin new --new` (#210; the skill uses the inferred name). The README follow-ups in #211. A `gp` pipeline that chains digest, scaffold, and fixtures into one command (orchestration stays in the skill).
